01진단 — 프로토타입이 증명한 것과 막히는 지점

아래는 추측이 아니라 AAS_Node_Composer.html의 실제 코드에서 읽어낸 제약입니다. 각 항목이 고도화 단계 하나에 대응합니다.

이미 옳게 되어 있는 것 — 포함 관계만을 간선으로 삼는 결정(connect()), AASd-120을 지키는 List 자식 idShort 생략(inList()), 주·보조 semanticId 분리(supRefs()), 그리고 무손실에 가까운 왕복(serialize() ↔ importJson()). 이 네 가지는 그대로 커널로 옮깁니다.

막히는 지점지금 코드에서결과푸는 단계
자식 순서를 표현할 수 없다 childrenOf()가 edges 배열의 삽입 순서를 그대로 반환 SubmodelElementList는 orderRelevant:true로 나가는데 사용자가 순서를 바꿀 방법이 없음. 왕복 시 순서 보존도 우연에 기댐 P1
실행취소가 없다 인스펙터 input 이벤트가 S.nodes를 직접 변형 오타 하나에 되돌릴 방법이 없어 실사용에서 가장 먼저 신뢰를 잃음 P1
키 입력마다 전체 재계산 render() → serialize() + validate() 전체 순회, DOM 전체 재도색 노드 수에 비례해 타이핑이 밀림. 500노드에서는 편집 불가 P1 · P4
좌표가 의미 데이터에 섞임 노드 객체 안에 x, y가 함께 저장 노드를 옮기기만 해도 문서가 바뀐 것으로 보여 버전 비교·병합이 무의미해짐 P1
conceptDescriptions가 항상 비어 나감 serialize()가 빈 배열이면 delete 수신 측이 단위·자료형을 알 수 없음. "45.2"가 ℃인지 ℉인지 모델 밖에 있음 P6
semanticId가 자유 문자열 인스펙터의 단순 text input 버전 접미사 오기입을 잡을 수 없음. 사양서에서 확인한 값과 사람이 찍은 값이 구분되지 않음 P6
노드 9종으로는 못 그리는 모델 TYPES에 Entity·Operation·Relationship·Blob 없음 Hierarchical Structures(BoM), Asset Interfaces Description 템플릿을 아예 표현할 수 없음 P2
속성 60개를 노드로 그린다 Nameplate 템플릿 삽입 = 노드 20여 개 생성 캔버스가 즉시 포화. 실제 설비는 서브모델당 수십~수백 요소 P5
검증 규칙을 손으로 구현 validate() 안의 AASd-022 · 108 · 120 자체 구현 나머지 수십 개 제약은 BaSyx 등록 시점에 처음 발견됨 P1
모델이 브라우저 한 곳에만 localStorage 단일 키에 통째 저장 공유·버전·감사 추적 불가. 캐시를 지우면 사라짐 P7
이 계획의 한 문장

프로토타입의 노드·간선 그래프를 순서를 가진 문서 트리 + 명령 로그로 바꾸면, 실행취소·버전·감사·일괄생성·협업이 각각의 기능이 아니라 한 설계의 부산물로 따라옵니다. 나머지 열 개 단계는 그 위에 얹는 일입니다.

02무엇이 "advanced"인가 — 다섯 가지 차별점

AASX Package Explorer를 웹으로 다시 만드는 것은 목표가 아닙니다. 아래 다섯 가지가 없으면 만들 이유가 없습니다.

01 · 커널

명령으로 편집한다

모든 변경이 Cmd 하나로 표현되고 역명령을 돌려줍니다. 에디터의 Ctrl+Z, 서버의 버전 로그, CSV 일괄 생성, n8n 노드가 전부 같은 명령을 씁니다.

02 · 편집

캔버스만 고집하지 않는다

구조는 캔버스, 대량 입력은 표, 키보드 작업은 트리. 세 뷰가 같은 문서를 보며 실시간 동기화됩니다. Nameplate 15개 항목을 노드로 그리게 하지 않습니다.

03 · 템플릿

템플릿이 계약으로 남는다

삽입 후에도 인스턴스가 템플릿 ID·버전을 기억합니다. 필수 요소 누락, 카디널리티 위반, semanticId 이탈을 계속 감시하고, 사양서 개정 시 마이그레이션을 안내합니다.

04 · 시맨틱

semanticId가 타입을 갖는다

IRDI·IRI를 파싱해 체계·코드·버전으로 분해하고, 사전 프록시가 실재·폐기 여부를 확인합니다. 확인됨 미확인 폐기됨 배지로 드러냅니다.

05 · 출력

단위까지 실어 보낸다

사용된 semanticId를 모아 conceptDescriptions를 자동 생성합니다. 수신 측이 사전을 다시 조회하지 않고도 단위와 자료형을 해석할 수 있어야 교환이 성립합니다.

03아키텍처 — 무엇이 무엇에 의존하는가

플레이북의 pnpm 모노레포 구성을 그대로 따르되, 패키지 두 개를 더 쪼갭니다. 이유는 각각 아래에 적었습니다.

패키지를 더 쪼개는 이유

  • @aas/aasx를 커널에서 분리 — AASX는 ZIP이라 커널의 "의존성 0" 원칙과 충돌합니다. 대신 fflate(브라우저·Node 공용)로 구현해 서버 없이도 브라우저에서 내보내기가 됩니다. 폐쇄망 현장에서 이 차이가 큽니다.
  • @aas/semantic을 분리 — IRDI 파싱은 순수 로직(커널이 씀)이고 사전 조회는 네트워크(웹·API가 씀)입니다. 한 패키지에 두되 파서와 클라이언트를 별도 엔트리로 내보내, 커널은 파서만 가져다 씁니다.
CI로 강제할 경계

@aas/kernel의 import 그래프에 react · next · hono · fflate · fetch가 나타나면 빌드를 실패시킵니다. 이 검사 하나가 이후 모든 재사용(CLI, 일괄 생성 워커, n8n 노드, Orange 애드온의 JSON 검증)을 지켜 줍니다.

04커널 설계 — 이 계획의 전부

P1에서 2주를 여기에 씁니다. 다른 열 단계를 다 미뤄도 이것만은 먼저 끝냅니다.

문서 모델 — 좌표와 의미를 분리한다

packages/kernel/src/model.ts
export type NodeId = string;

/* 의미 문서 — 이것만이 버전·비교·해시의 대상 */
export interface AasDoc {
  schema: 1;
  nodes:  Record<NodeId, AasNode>;
  order:  Record<NodeId, NodeId[]>;   부모 → 자식. 배열 순서가 곧 모델 순서
  parent: Record<NodeId, NodeId | null>;
  roots:  NodeId[];
}

/* 화면 문서 — 별도 저장. 실행취소·diff·해시에서 제외 */
export interface Layout {
  pos:       Record<NodeId, { x: number; y: number }>;
  collapsed: Record<NodeId, boolean>;
}

바뀌는 것 — 프로토타입의 edges 배열이 사라지고 order 맵이 들어옵니다. 부모 하나당 자식 배열 하나이므로 순서 변경이 배열 splice 한 번이고, SubmodelElementList의 orderRelevant가 비로소 의미를 갖습니다. 좌표는 Layout으로 빠져, 노드를 옮겼다고 문서가 더러워지지 않습니다.

명령 — 실행취소·버전·자동화가 한 지점에서 나온다

packages/kernel/src/command.ts
export type Cmd =
  | { t:'insert';   parent:NodeId|null; index:number; node:AasNode }
  | { t:'remove';   node:NodeId }
  | { t:'move';     node:NodeId; parent:NodeId; index:number }
  | { t:'set';      node:NodeId; path:string; value:Json }
  | { t:'template'; templateId:string; version:string; parent:NodeId|null }
  | { t:'batch';    label:string; cmds:Cmd[] };        한 번의 실행취소 단위

export function apply(doc: AasDoc, cmd: Cmd):
  { doc: AasDoc; undo: Cmd[]; rejected?: Reject };

/* 거부는 예외가 아니라 값. 사유를 코드로 돌려준다 */
export type Reject =
  { code:'CONTAINMENT'; parent:AasNodeType; child:AasNodeType }
  | { code:'CYCLE' } | { code:'ALREADY_PARENTED' } | { code:'LIST_TYPE_MISMATCH' };

프로토타입의 connect()가 한국어 문자열을 반환하던 자리에 판별 가능한 코드가 들어갑니다. UI는 코드를 메시지로 번역하고(ko/en), 테스트는 문자열이 아니라 코드로 단언하며, 서버는 같은 코드로 일괄 생성 실패 리포트를 만듭니다.

명령 하나로 따라오는 것들

기능구현추가 비용
실행취소 / 다시실행undo 스택에 역명령 push거의 없음
버전 · 감사 추적서버가 명령 로그를 append, N개마다 스냅샷스냅샷 정책만
버전 비교 (diff)두 버전 사이 명령 목록을 사람이 읽는 문장으로렌더러만
CSV 일괄 생성행 하나 → 명령 배열 → apply 반복매핑 UI만
낙관적 잠금 병합충돌 시 상대 명령을 내 문서에 재적용 시도충돌 해소 화면
실시간 협업 (선택)명령을 CRDT 연산으로 승격요구가 확인된 뒤에

직렬화 계약 — 테스트로 못 박는다

왕복 불변식
serialize(doc)          → Environment
parse(env)              → { doc, warnings[] }
canonicalize(env)       → Environment   키 정렬 · 빈 배열 제거 · 공백 정규화

∀ doc:  parse(serialize(doc)).doc  ≡  doc                    구조 동등
∀ env:  canonicalize(serialize(parse(env).doc))  ≡  canonicalize(env)  의미 동등

canonicalize()를 커널이 제공하는 것이 핵심입니다. Package Explorer가 만든 AASX의 JSON은 키 순서와 빈 배열 처리가 우리와 다릅니다. 텍스트를 비교하면 영원히 실패하지만, 정규화 후 비교하면 "우리 도구가 남의 파일을 손상시키지 않는다"를 CI에서 증명할 수 있습니다.

검증 4계층 — 무엇을 누가 판단하는가

계층담당예시실행 시점
L0 구조커널 명령포함 규칙 위반, 순환 참조 — 애초에 만들 수 없음편집 즉시 (거부)
L1 규격aas-core3.0AASd-002 · 022 · 108 · 120 …증분 · 30ms 이내
L2 정책사내 규칙IRI 네임스페이스 규약, 필수 서브모델 존재, 명명 컨벤션증분
L3 템플릿@aas/templates필수 요소 누락, 카디널리티, semanticId 이탈증분

프로토타입의 validate()에 섞여 있던 규격 제약(AASd-022·108·120)은 L1으로 이관하고 지웁니다. 남는 것은 L2뿐입니다. 이슈는 모두 같은 모양을 갖습니다.

packages/kernel/src/issue.ts
export interface Issue {
  code:     string;                 'AASd-022' | 'POL-IRI-001' | 'T-002' | 'DIC-004'
  layer:    'core'|'policy'|'template'|'dictionary';
  severity: 'error'|'warn'|'info';
  node:     NodeId;
  path:     string;                 Submodel/TechnicalProperties/RatedPower
  message:  { ko:string; en:string };
  quickFix?: { label:string; cmds:Cmd[] };   클릭 한 번으로 고치기
}

quickFix가 고도화의 실질입니다. "semanticId 없음" 경고에 사전에서 찾아 채우기, "필수 요소 누락"에 템플릿에서 생성하기, "폐기된 IRDI"에 후속 버전으로 갱신하기를 명령 배열로 붙입니다. 지적만 하는 검증은 결국 무시됩니다.

증분 검증 — 타이핑을 막지 않는 방법

노드마다 서브트리 해시를 캐싱하고, 변경된 노드의 조상 체인만 다시 직렬화·검증합니다. 2,000노드 문서에서 속성 값 하나를 고칠 때 재계산 대상은 보통 3~5개 서브트리입니다. JSON 미리보기는 100ms 디바운스로 바뀐 서브모델만 다시 그립니다.

derivedFromShell 인스펙터Type Shell로부터 파생 — 설비 100대 일괄 생성의 기반
파싱에서 잃고 있는 것

현재 importJson()은 위 항목을 전부 버립니다. 남의 AASX를 열어 저장하면 조용히 정보가 사라집니다. P2가 끝나기 전까지는 "가져오기"를 읽기 전용으로 두거나, 파싱하지 못한 필드를 노드에 _raw로 보존해 그대로 다시 내보내는 편이 안전합니다. 후자를 권합니다.

06시맨틱 자동화 — semanticId에 타입을 준다

첨부 AAS_semanticId_정리.html의 분석을 코드로 옮기는 단계입니다. 사람이 사전을 검색해 문자열을 복사하는 일을 도구가 대신합니다.

결정 반영 · eCl@ss 미보유

사전 조회는 IEC CDD 단독으로 설계합니다. eCl@ss IRDI는 입력·보존·출력은 정상 동작하되 실재·버전 검증만 불가능하며, 그 값들은 사양서 대조 여부에 따라 사양서 확인 또는 미확인으로 남습니다. 사전 어댑터는 DictAdapter 인터페이스로 분리해, 나중에 회원 자격이 생기면 어댑터 하나를 더 붙이는 것으로 끝나게 둡니다.

packages/semantic/src/parse.ts
export interface SemanticRef {
  raw:     string;
  scheme:  'iec-cdd' | 'eclass' | 'iri' | 'unknown';
  code?:   string;      ABA565
  version?:string;      009  — 끝 세 자리가 사고를 낸다
  status:  'confirmed' | 'unverified' | 'deprecated' | 'unknown';
  checkedAt?: string;
}

eCl@ss  0173-1#02-AAO677#002    ICD-OI#CSI-Code#VI
IEC CDD 0112/2///61987#ABA565#009    슬래시 개수가 하나만 틀려도 다른 식별자
IDTA    https://admin-shell.io/idta/nameplate/3/0/Nameplate

상태 배지 — 어디서 온 값인지, 무엇으로 확인했는지

eCl@ss를 조회할 수 없게 되면서 "확인됨"을 둘로 쪼개는 것이 중요해졌습니다. 사양서에서 눈으로 대조한 값과 사전이 기계적으로 확인해 준 값은 신뢰 수준이 다릅니다.

상태의미어떻게 얻어지나
사전 확인IEC CDD에서 실재·현행 확인사전 프록시 조회 성공. checkedAt 기록
사양서 확인IDTA 사양서에서 사람이 대조템플릿 JSON의 "verified":"spec". eCl@ss 보조 식별자 대부분이 여기
미확인입력했으나 아직 대조되지 않음인스펙터 직접 입력의 기본 상태. 내보내기 요약에 건수 표시
폐기됨사전에서 superseded 처리사전 프록시가 후속 버전을 함께 반환 → 퀵픽스로 갱신
자체 IRI사내 도메인 발급정책(L2)이 네임스페이스 규약 준수를 검사

첨부 문서가 권고한 자체 IRI 규약 https://{도메인}/ids/cd|sm|aas|asset/…을 L2 정책 규칙 POL-IRI-001로 코드화합니다. 개념 정의와 인스턴스 네임스페이스가 섞이면 경고합니다.

현행 6종을 위 스키마로 옮기고, 플레이북의 template-harvester 서브에이전트로 2종을 추가합니다 — Hierarchical Structures(02011-1-1)와 Asset Interfaces Description(02017-1-1). 후자는 OPC UA·MQTT 접점을 기술하므로 P8의 n8n 연동과 P9 대시보드의 데이터 경로 근거가 됩니다. 사양서에서 직접 확인하지 못한 semanticId는 "verified":"none"으로 남기고 UI에 미확인 배지를 띄웁니다. 추측한 값을 조용히 넣지 않는 것이 규칙입니다. eCl@ss 조회가 불가능해진 만큼, 템플릿 harvest 시 사양서 페이지 번호까지 함께 기록해 두면 나중에 재대조가 쉬워집니다.

08에디터 — 세 개의 뷰, 하나의 문서

캔버스 하나로 버티려는 순간 도구가 무너집니다. 작업의 성격마다 맞는 뷰가 다릅니다.

뷰무엇에 쓰나구현
캔버스구조를 만든다 — Shell·Submodel·Collection의 관계, BoM 계층React Flow + ELK 자동 정렬(Web Worker). 서브트리 접기, 뷰포트 밖 미렌더
트리탐색하고 옮긴다 — 키보드만으로 생성·이동·편집. 접근성 대체 경로 겸 대형 모델의 실사용 경로가상 스크롤. 방향키·Enter·F2·Ctrl+↑↓로 순서 변경
표대량으로 채운다 — 선택한 Submodel·Collection의 자식을 스프레드시트로. 붙여넣기 지원열: idShort · modelType · semanticId · valueType · value. 열 단위 일괄 편집

세 뷰는 같은 AasDoc을 보고 같은 Cmd를 냅니다. 선택 상태도 공유하므로 캔버스에서 고른 노드가 트리에서 펼쳐지고 표에서 강조됩니다. 검증 이슈 클릭 시 현재 뷰에서 해당 노드로 이동합니다.

표 뷰가 실질입니다

Nameplate 하나가 요소 15개, Technical Data가 중첩 포함 12개입니다. 설비 한 대에 서브모델 5개면 노드 70~100개입니다. 이것을 캔버스에서 그리게 하면 아무도 쓰지 않습니다. 캔버스는 서브모델 수준 구조만 보여주고, 그 안은 표로 채우는 것이 실제 작업 흐름입니다.

캔버스는 접근성이 구조적으로 취약합니다. 트리 뷰를 완전한 대체 경로로 만들어 생성·연결·편집·삭제가 전부 키보드로 가능해야 합니다. 상태는 색만으로 구분하지 않고 pill 라벨과 아이콘 형태를 함께 씁니다. 포커스 링은 캔버스 노드에도 보여야 합니다.

공동 편집이 요구가 아니므로 병합 화면과 CRDT 준비를 걷어냅니다. 충돌은 한 사람이 탭 두 개를 연 경우뿐이라 ETag 409 + "다시 불러오기"로 충분합니다. 다만 명령 로그 자체는 유지합니다 — 버전 비교, "누가 언제 무엇을 바꿨는가", 잘못된 일괄 변경 되돌리기가 전부 여기서 나오고, 이것은 사용자 수와 무관한 가치입니다.

AASX 패키징

OPC 패키지 구조는 첨부 문서에 정리된 그대로입니다. @aas/aasx가 브라우저·서버 양쪽에서 같은 코드로 조립합니다.

machine_001.aasx
├─ [Content_Types].xml
├─ _rels/.rels
└─ aasx/
   ├─ aasx-origin
   ├─ _rels/aasx-origin.rels
   ├─ data/environment.json      serialize() 결과 그대로
   └─ files/                     File 요소가 가리키는 첨부

완료 기준은 AASX Package Explorer로 열린다이고, 이를 CI에서 확인할 수 없으므로 구조 검사 테스트 + 사람이 한 번 여는 수동 확인을 병행합니다. 자동화 가능한 대체 검사는 basyx-python-sdk의 AASX reader로 읽어 의미 동등을 확인하는 것입니다.

BaSyx 게시

{smId}는 전역 id의 Base64URL 인코딩입니다. 값 갱신 경로 PATCH /submodels/{smId}/submodel-elements/{path}/$value가 n8n 연동의 접점이 됩니다. 게시는 셸·서브모델 단위로 부분 성공을 허용하고, 실패 항목만 재시도할 수 있어야 합니다.

운전 데이터는 AAS에 담지 않는다

플레이북의 판단을 그대로 따릅니다. n8n이 설비에서 읽어 시계열 저장소(TimescaleDB)에 적재하고 대시보드는 그것을 읽습니다. AAS는 구조와 의미의 원본이지 시계열 데이터베이스가 아닙니다. Time Series Data 서브모델에는 구간 메타데이터와 저장소 참조만 둡니다.

P0실측 — 계획을 싸게 고치는 단계1주

지금 프로토타입으로 실제 설비 3대를 끝까지 모델링합니다. 어떤 노드가 없어서 막히는지, 어떤 검증이 성가신지가 그 자리에서 드러납니다. 재작성 범위를 정하는 가장 싼 방법입니다.

P1커널 — 문서 모델 · 명령 · 무손실 왕복2주

프로토타입의 model·serialize·parse·validate를 @aas/kernel로 옮기면서 order 맵 도입, Layout 분리, 명령 도입, aas-core3.0 위임을 동시에 합니다. 나눠서 하면 두 번 옮기게 됩니다.

P2메타모델 커버리지 — 노드 6종 · 부속 필드2주

Entity · Relationship · AnnotatedRelationship · Operation · Blob · Capability와 qualifiers · extensions · administration · specificAssetIds. 순서는 model → serialize → parse → validate → 노드 컴포넌트 → 골든 테스트, 하나라도 빠지면 왕복이 깨집니다.

P3템플릿 엔진 — 정의 · 적합성 · 마이그레이션2.5주

설비 수십 대 규모에서는 일괄 생성보다 템플릿 품질이 훨씬 큰 가치입니다. 반나절 늘려 harvest 결과를 사양서와 두 번 대조하고, 확인 출처(사양서·페이지)를 템플릿 JSON에 남깁니다.

P4에디터 셸 — 캔버스 · 트리 · 인스펙터 · 실행취소3주
P5표 편집 · 검증 퀵픽스2주
P6시맨틱 — IEC CDD 프록시 · ConceptDescription1.5주

어댑터가 IEC CDD 하나뿐이고 오프라인 시드 번들이 빠져 반주 줄었습니다. 대신 사내 용어 ↔ IRDI 매핑 20~30건을 이 단계에서 확보합니다.

P7서버 — 저장소 · 버전 · AASX · BaSyx V22주

단일 사용자 결정으로 병합 화면과 CRDT 준비가 빠졌습니다. BaSyx는 V2(AAS V3 API) 기준이므로 계획서 09장의 엔드포인트를 그대로 씁니다.

P8n8n 노드 팩 · 최소 일괄 생성1주

대상이 수십 대이므로 매핑 UI를 만들지 않습니다. 템플릿별 고정 컬럼 CSV만 받고, 실패 행은 건너뛰어 리포트에 남깁니다. 무게중심은 n8n 노드 팩 — AAS Read Submodel / Write SubmodelElement / Watch Model 세 개이고, 이것이 P9 대시보드의 데이터 경로가 됩니다.

P9대시보드 2종3주

모델 자산 관리(표준 준수 히트맵·검증 이슈 큐·사전 사용 현황)와 설비 운전 모니터링(수집 지연을 1급 지표로). 화면 설계는 플레이북 06장을 그대로 씁니다.

P10접근성 · 다국어 · 배포1.5주

키보드 전용 경로 완성, next-intl로 ko/en (UI 언어와 AAS 데이터 언어를 분리해 다룸), Docker Compose 단일 스택 설치. 인터넷 접근이 가능하므로 폐쇄망 오프라인 이미지는 만들지 않습니다 — 다만 사전 캐시는 PostgreSQL 볼륨에 남으므로 일시적 단절에는 그대로 견딥니다.

12확정된 결정과 리스크

P0의 결정 5건이 확정되어 아래와 같이 반영했습니다. 각 결정이 어느 단계를 어떻게 바꿨는지 함께 적었습니다.

결정확정계획에 반영된 것
eCl@ss 사전 미보유 사전 조회는 IEC CDD 단독. eCl@ss IRDI는 입력·보존·출력만 지원하고 검증하지 않음. 배지를 사전 확인 / 사양서 확인으로 분리. DictAdapter 인터페이스로 분리해 추후 확장 여지를 남김 06장 · P6
망 환경 인터넷 접근 가능 사전 프록시는 실시간 조회 + 캐시. 폐쇄망 시드 번들과 오프라인 설치 이미지를 범위에서 제외 P6 −0.5주 · P10 −0.5주
동시 편집 단일 사용자 병합 화면과 CRDT 준비 제외. 충돌은 ETag 409 + 재적재 안내. 명령 로그·버전·감사 추적은 유지 — 사용자 수와 무관한 가치 P1 단순화 · P7 −1주
BaSyx V2 (AAS V3 API) 09장의 엔드포인트·Base64URL 식별자·$value 갱신 경로가 그대로 적용. 버전 어댑터 불필요 P7 · P8
대상 규모 수십 대 (10~50) CSV 매핑 UI를 만들지 않고 고정 컬럼 최소 구현. 그 시간을 템플릿 품질과 표 편집으로 이전 P3 +0.5주 · P8 −1주
규모 결정이 바꾸는 것 하나

설비 10~50대라면 자동화보다 사람이 손으로 채우는 시간이 압도적입니다. 따라서 이 프로젝트의 성패는 P8(일괄 생성)이 아니라 P3(템플릿이 얼마나 정확한가)와 P5(표에서 얼마나 빨리 채우는가)에 걸립니다. 이 둘의 완료 기준을 느슨하게 넘기지 마십시오.

리스크영향대응
커널 재설계를 미루고 UI부터 만듦검증 로직이 컴포넌트에 흩어져 되돌릴 수 없음P1을 건너뛰지 않음. P4 이전에 커널 계약을 테스트로 고정

eCl@ss IRDI를 검증할 수 없다 확정 리스크템플릿의 보조 식별자가 사양서 오독이어도 발견되지 않음harvest 시 사양서 페이지를 함께 기록하고 두 사람이 대조. IEC CDD에 같은 개념이 있으면 주 식별자로 승격
IEC CDD에 한글 표제어가 없다현장 용어로 검색이 안 되어 사전 기능을 쓰지 않게 됨P6에서 사내 용어 ↔ IRDI 매핑 20~30건을 함께 만든다. 이것이 사전 기능의 실사용 여부를 가른다
표 뷰가 캔버스와 어긋남같은 문서인데 다르게 보임 — 신뢰 상실세 뷰가 같은 AasDoc·Cmd만 쓰도록 강제. 파생 상태 저장 금지
